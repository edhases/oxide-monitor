**Дата:** 18.11.2026  
**Контекст:** Проєктування дій миші, сучасної інтерактивної Flyout-панелі (розширеного Tooltip у стилі Windows 11), магнітного позиціонування, мультимоніторності, коректної роботи з `Auto-hide` таскбаром та гнучкого `Game Mode`.

## 1. Система дій миші та взаємодій (`[interactions]`)

У поточній версії `oxide-ui/src/window.rs` подвійний клік перемикає видимість віджета, а правий клік відкриває контекстне меню. Для повноцінного UX переходимо до повністю конфігурованої таблиці дій миші:

### 1.1. Підтримувані події на віджеті
| Подія Win32 | Поле конфіга | Рекомендована дія за замовчуванням |
|---|---|---|
| Лівий клік (`WM_LBUTTONUP` без drag) | `left_click` | `toggle_flyout` (закріпити/відкрити розширену картку) |
| Подвійний лівий клік (`WM_LBUTTONDBLCLK`) | `double_click` | `open_task_manager` (паритет із TrafficMonitor) |
| Середній клік (`WM_MBUTTONUP`) | `middle_click` | `open_settings` (швидкий вхід у налаштування) |
| Правий клік (`WM_RBUTTONUP`) | `right_click` | `context_menu` (системне меню) |
| Коліщатко миші (`WM_MOUSEWHEEL`) | `wheel_action` | `none` (опційно: `cycle_preset` або `cycle_page` — перемикання між сторінками метрик!) |

> **Зауваження щодо `left_click` vs `double_click`:** якщо обидві дії активні, одиночний клік можна або відкладати на `GetDoubleClickTime()` (до 250–300 ms — відчувається мляво), або робити `left_click` миттєвим, але при спрацьовуванні `WM_LBUTTONDBLCLK` автоматично ховати щойно відкритий Flyout перед запуском Task Manager. Другий варіант відчувається миттєвим і не створює затримок.

### 1.2. Каталог вбудованих дій (`ClickAction`)
- `none` — нічого не робити.
- `toggle_flyout` — відкрити / закріпити розширену Flyout-панель.
- `open_task_manager` — запуск `taskmgr.exe` через `ShellExecuteW` (`open`, без підвищення прав з нашого боку; ОС сама обробить UAC якщо потрібно).
- `open_resource_monitor` — запуск `perfmon.exe /res`.
- `open_network_stats` — відкрити `oxide-settings.exe --tab network-stats` (детальна статистика адаптерів та історія трафіку по днях/місяцях).
- `open_settings` — запуск (або активація вже відкритого) `oxide-settings.exe`.
- `toggle_game_mode` — ручне вмикання/вимикання Game Mode.
- `cycle_preset` — циклічне перемикання між вибраними пресетами користувача (напр. «Мінімалізм 1 рядок» ↔ «Геймерський з графіками»).
- `copy_summary` — скопіювати поточний знімок метрик у буфер обміну в читабельному форматі (зручно для баг-репортів або чату).
- `run_command { path, args }` — запуск довільної програми користувача (напр. HWiNFO, Process Explorer, Windows Terminal). Для безпеки при запуску використовується `CreateProcessW` без проходження через `cmd.exe /c` (виключає shell injection).

### 1.3. Захист фокусу
Зберігається поточна поведінка `WM_MOUSEACTIVATE => MA_NOACTIVATE` і стиль `WS_EX_NOACTIVATE`: наведення або клік на віджет **ніколи не забирає фокус** у активного вікна (редактора коду, браузера, гри у віконному режимі), окрім випадків, коли користувач викликав контекстне меню або відкрив зовнішню програму.

## 2. Інтерактивний розширений Tooltip (Win11 Flyout-панель)

### 2.1. Архітектура та бюджет пам'яті
Стандартний Win32 `TOOLTIPS_CLASS` не підтримує сучасні картки, графіки, сітку ядер CPU, темний Acrylic і клікабельні кнопки. З іншого боку, запускати `oxide-settings.exe` (egui + wgpu) при наведенні курсора надто повільно (100–160 ms і 45 MB RAM).

**Рішення:** власне легке popup-вікно **`OxideFlyout`** всередині `oxide-monitor.exe`, яке рендериться через той самий **`oxide-render` (Direct2D + DirectWrite)** у DIB + `UpdateLayeredWindowIndirect` (або D2D поверх `DWMWA_SYSTEMBACKDROP_TYPE = DWMSBT_TRANSIENTWINDOW` Acrylic + `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND`):

- **Час відкриття:** `< 12 ms` (миттєвий відгук, як системний Flyout календаря/мережі у Windows 11).
- **Пам'ять у відкритому стані:** ~`1.5–2.5 MB` (DIB `380 × 480 px` при 100% DPI ≈ 730 KB; при 150% DPI ≈ 1.6 MB).
- **Пам'ять після закриття:** через `5 секунд` після приховування DIB-буфер і кеш layout Flyout **звільняються (`Option<FlyoutSurface> = None`)** → `0 B` у спокої!
- **Частота оновлення:** 1 Hz (тільки поки Flyout видимий); коли схований — не рендериться і не алокує пам'ять.

### 2.2. Поведінка наведення та інтерактивність
Щоб користувач міг не просто «подивитися», а й взаємодіяти з карткою (клікнути «Налаштування», перемкнути Game Mode, навестися на окремий диск):
1. **Тригер відкриття:**
   - `hover`: `TrackMouseEvent(TME_HOVER | TME_LEAVE)` із налаштовуваною затримкою `hover_delay_ms = 350` (або `0` щоб вимкнути відкриття по наведенню і відкривати лише по кліку).
   - `click`: миттєве відкриття в «закріпленому» (pinned) стані до кліку поза межами Flyout або натискання `Esc`.
2. **Safe Transition (перехід миші з віджета на Flyout):**
   - Коли курсор покидає віджет (`WM_MOUSELEAVE`), запускається grace-таймер **250 ms**. Якщо протягом 250 ms курсор заходить у прямокутник Flyout (або у «місток» між віджетом і Flyout) — вікно залишається відкритим і стає інтерактивним.
   - При виході курсора за межі обох вікон — плавне зникнення (або миттєве при системному `Reduced Motion`).
3. **Розумне позиціонування:**
   - Обчислюється монітор віджета через `MonitorFromWindow(overlay_hwnd, MONITOR_DEFAULTTONEAREST)` і його `rcWork`.
   - Якщо таскбар знизу — Flyout відкривається **над** віджетом із відступом `8 px` і вирівнюється по центру віджета, притискаючись до країв `rcWork` (`margin = 8 px`), щоб ніколи не виходити за межі екрана.
   - Аналогічно для верхнього (`ABE_TOP` → під віджетом), лівого (`ABE_LEFT` → праворуч) і правого (`ABE_RIGHT` → ліворуч) таскбара.

## 3. Позиціонування, магнітне прилипання та мультимоніторність

### 3.1. Режими прив'язки (`taskbar.anchor`)

Поточний `window.rs` вміє ставити віджет лише ліворуч від `TrayNotifyWnd`. Розширюємо геометрію до 4 надійних режимів:

1. **`tray_left` (Дефолт):** ліворуч від `TrayNotifyWnd` (`tray_rect.left - width - margin + x_offset`), вертикально по центру таскбара. Якщо `TrayNotifyWnd` відсутній (наприклад, на secondary taskbar) — fallback на `taskbar_rect.right - right_space - width`.
2. **`taskbar_left` (Лівий край / Win11 з центрованими іконками):**
   - На Windows 11, коли кнопки задач по центру, ліва зона таскбара часто порожня (або містить лише кнопку Widgets).
   - Позиція: `taskbar_rect.left + left_space + x_offset` (де `left_space` або визначається автоматично через перевірку наявності Widgets-елемента / UIA один раз при зміні геометрії, або задається вручну, default `160 px` при Widgets on / `12 px` при Widgets off).
3. **`taskbar_right`:** притиснуто до правого краю (з урахуванням системного годинника на secondary taskbar).
4. **`free_drag` (Вільне перетягування по таскбару з магнітним снапом):**
   - Коли `lock_position = false`, користувач може перетягувати віджет лівою кнопкою миші (або `Alt + Drag`, щоб уникнути випадкових зсувів!).
   - Під час перетягування діє **магнітне прилипання** (`snap_distance = 8 px`) до:
     - лівої межі `TrayNotifyWnd`;
     - лівого краю таскбара (та межі `left_space`);
     - вертикального центру таскбара;
     - центру монітора.
   - При відпусканні координати зберігаються як `(anchor, x_offset, y_offset)` відносно поточного монітора/таскбара (у логічних DIP, щоб не «з'їжджали» при зміні DPI!).

### 3.2. Вибір монітора та Multi-DPI
- Замість крихкого `index = 0/1`, який Windows може змінювати після сну або підключення HDMI, монітор ідентифікується структурою:
  - `monitor = "primary"` (дефолт);
  - `monitor = { device = "\\\\.\\DISPLAY2", friendly_name = "DELL U2723QE" }` (співставляється через `EnumDisplayMonitors` + `GetMonitorInfoW` + `QueryDisplayConfig` для читабельної назви в UI);
  - `monitor = "all_taskbars"` (опційно в майбутньому: окремий overlay-екземпляр на кожному моніторі з власним `HMONITOR` та власним DPI).
- При відключенні вибраного зовнішнього монітора (ноутбук від'єднали від док-станції) віджет **автоматично і без падіння** тимчасово переїжджає на `primary`, а після повторного підключення того ж монітора (`WM_DISPLAYCHANGE`) повертається на нього.
- Усі розміри та зсуви зберігаються у **DPI-незалежних одиницях (DIP, 96 DPI baseline)** і масштабуються через `GetDpiForMonitor` / `WM_DPICHANGED` — це виправляє проблему розмиття і зсувів при мішаних моніторах (напр. ноутбук 150% + зовнішній 100%).

## 4. Коректна робота з `Auto-hide` панеллю задач

На відміну від TrafficMonitor, який крутив 100 ms таймер (що спалювало CPU), Oxide Monitor використовує **подієвий підхід Windows Accessibility (`SetWinEventHook`)**:

1. **Детекція стану Auto-hide:**
   - Виклик `SHAppBarMessage(ABM_GETSTATE, &mut abd)` перевіряє прапорець `ABS_AUTOHIDE`.
   - Повторна перевірка відбувається лише при `WM_SETTINGCHANGE`, `WM_DISPLAYCHANGE` та `TaskbarCreated`.
2. **Відстеження руху таскбара (0% CPU у спокої):**
   - Якщо `ABS_AUTOHIDE` активний, реєструється out-of-context hook (`WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS` — **не інжектить DLL у чужі процеси**, 100% безпечно для античитів!) на `EVENT_OBJECT_LOCATIONCHANGE` для `dwProcessId` процесу `Shell_TrayWnd`.
   - Коли таскбар ховається або виїжджає, Windows сама надсилає нам подію на UI-потік.
   - Ми перевіряємо видиму частку `taskbar_rect ∩ monitor_rect`:
     - Якщо перетин по висоті (для bottom/top) або по ширині (для left/right) `≤ 4 px` → таскбар вважається **прихованим**.
     - Якщо перетин `> 4 px` → таскбар **видимий** (і `y` віджета синхронізується з поточним `taskbar_rect`).
3. **Налаштовувана поведінка користувача (`taskbar.autohide_behavior`):**
   - `hide_with_taskbar` *(рекомендований дефолт)*: віджет миттєво ховається (`SW_HIDE`) і **призупиняє рендеринг**, коли таскбар схований; з'являється, щойно користувач підводить мишу до краю екрана.
   - `keep_visible`: віджет залишається видимим у куті екрана навіть при схованому таскбарі (корисно для тих, хто хоче бачити метрики постійно, але мати максимум місця на екрані; у цьому режимі автоматично активується приховування у fullscreen).

## 5. Game Mode та розумні правила автоприховування (`[game_mode]`)

### 5.1. Подієва детекція fullscreen та процесів ігор (без CPU polling!)
Замість щосекундного сканування всіх процесів системи (`CreateToolhelp32Snapshot`), Oxide Monitor поєднує два надлегких механізми:

1. **Системна детекція fullscreen:**
   - `SHQueryUserNotificationState` (`QUNS_RUNNING_D3D_FULL_SCREEN`, `QUNS_BUSY`, `QUNS_PRESENTATION_MODE`) — уже є в `window.rs`.
   - **Доповнення для Borderless Fullscreen** (сучасні ігри на DX12/Vulkan майже завжди працюють у Borderless Windowed, де `SHQueryUserNotificationState` часто повертає `QUNS_ACCEPTS_NOTIFICATIONS`!):
     - При зміні активного вікна (`EVENT_SYSTEM_FOREGROUND`) береться `fg = GetForegroundWindow()`.
     - Перевіряється, чи не є `fg` системним вікном (`Progman`, `WorkerW`, `Shell_TrayWnd`, `Shell_SecondaryTrayWnd`).
     - Порівнюється `GetWindowRect(fg)` із `MONITORINFO.rcMonitor` того монітора, на якому знаходиться віджет (`fg_rect` повністю покриває `rcMonitor`, і вікно не має рамки `WS_CAPTION` або є D3D-вікном). Якщо так — активується приховування на цьому моніторі (але на *другому* моніторі, якщо віджет стоїть там, віджет **залишається видимим**!).

2. **Правила за списком ігор/процесів (`game_mode.process_rules`):**
   - Подієво на `EVENT_SYSTEM_FOREGROUND` (коли змінюється активне вікно — це кілька подій на хвилину, **~0.00% CPU**!):
     1. `GetWindowThreadProcessId(fg, &mut pid)`.
     2. `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, false, pid)` — працює без admin для більшості ігор (якщо гра під захистом античиту повертає `ERROR_ACCESS_DENIED`, це саме по собі корисний fallback-сигнал при borderless fullscreen, або ім'я береться через `QueryFullProcessImageNameW` там, де дозволено, не падаючи при відмові).
     3. Порівняння імені exe / шляху з правилами користувача:
        - точне ім'я: `cs2.exe`, `dota2.exe`, `cyberpunk2077.exe`;
        - glob-маска: `valorant*.exe`, `*\steamapps\common\*`, `*\Epic Games\*`.
   - Опційно підтримується **Whitelist (ігнорувати fullscreen)** для програм, де користувач хоче бачити віджет (напр. `mstsc.exe` або `vmware.exe`).

### 5.2. Рівні дії Game Mode (`game_mode.action`)
Коли Game Mode активовано (вручну з трею/Flyout, або автоматично за правилом):

| Рівень | Що відбувається | Навіщо |
|---|---|---|
| `hide_only` | Ховається overlay та Flyout, зупиняється рендеринг (`0` UI-циклів) | Максимально чисто під час відео/презентацій/ігор |
| `hide_and_low_power` *(дефолт)* | `hide_only` + призупиняється опитування NVML/ADLX та PDH GPU (жодних звернень до відеодрайвера під час гри!) | Усуває будь-які мікрофрізи (frame pacing stutter), які інколи спричиняють часті виклики NVML/PDH у деяких іграх |
| `strict_anticheat` | `hide_and_low_power` + зупинка зовнішнього PawnIO helper (коли буде додано в Phase 4) і відключення читання SHM | Максимальна сумісність з агресивними античитами (`EAC / BattlEye / Vanguard / FACEIT`) |

### 5.3. Додаткові політики полірування (Polish)
- **Сон / блокування екрана:** підписка на `WTSRegisterSessionNotification` (`WTS_SESSION_LOCK` / `WTS_SESSION_UNLOCK`) та `WM_POWERBROADCAST` (`PBT_APMSUSPEND` / `PBT_APMRESUMEAUTOMATIC`) — при заблокованому екрані або вимкненому дисплеї сенсорний потік переходить у сплячий режим, а при виході зі сну акуратно переініціалізує PDH/мережу/провайдерів.
- **Click-through (`mouse_penetrate`):** опція пропускати всі кліки крізь віджет (`WS_EX_TRANSPARENT`); при затиснутій клавіші `Alt` (або з іконки в треї) кліки знову перехоплюються, щоб віджет неможливо було «втратити».
- **Візуальний зворотний зв'язок у треї:** при активному ручному Game Mode іконка в треї отримує subtle badge (або змінений tooltip `Oxide Monitor — Ігровий режим (приховано)`), щоб користувач завжди розумів, чому віджета немає на таскбарі.
