# Дослідження 02: Рушій повної кастомізації віджета Oxide Monitor

**Дата:** 18.11.2026  
**Контекст:** Розширення поточної моделі `oxide-core` (`Config` v1, 12 `ItemId`, фіксований 2-рядковий GDI-рендер) до декларативного рушія кастомізації на базі Direct2D + DirectWrite, що перевершує можливості TrafficMonitor.  
**Пов'язані файли коду:** [`config.rs`](../../crates/oxide-core/src/config.rs), [`metrics.rs`](../../crates/oxide-core/src/metrics.rs), [`layout.rs`](../../crates/oxide-ui/src/layout.rs), [`render.rs`](../../crates/oxide-ui/src/render.rs).

## 1. Обмеження поточної моделі та TrafficMonitor

У поточній реалізації Oxide Monitor (Phase 0) та у класичному TrafficMonitor існують структурні обмеження:

| Аспект | TrafficMonitor (1.8.6) | Oxide Monitor (v1 / Phase 0) | Ціль Oxide Monitor (v2) |
|---|---|---|---|
| **Макет** | Жорсткі 1 або 2 рядки; однакова ширина колонок; порядок за фіксованим списком 13 елементів | `rows = 1..4`, column-major, рівна ширина колонок | 1/2/3/4 рядки, вертикальний таскбар, довільна сітка (`grid` з `row_span`/`col_span`), логічні групи з індивідуальною шириною |
| **Мульти-залізо** | 1 активний диск, 1 GPU (пріоритет жорстко зашитий у коді), 1 мережевий адаптер | `Snapshot` уже збирає `gpus: Vec<GpuSample>` і `disks: Vec<DiskSample>`, але `ItemId` бачить лише primary | Довільна кількість конкретних метрик одночасно (напр. iGPU + dGPU, NVMe C: + SATA D:, Wi-Fi + VPN) через `MetricSelector` |
| **Візуалізація елемента** | Текст + глобальний фоновий бар або окремий графік швидкості | Тільки текст | 4 режими на кожен елемент: `text`, `text_sparkline`, `text_progress` (лінійний/радіальний), `graph_only` (вкл. dual-series) |
| **Типографіка** | Один шрифт на весь віджет; цифри «стрибають» у пропорційних шрифтах | Один `HFONT` (GDI) | Окремі `FontSpec` для label / value / unit; DirectWrite `tabular-nums` (`tnum`) без стрибків цифр |
| **Кольори** | Статичний колір на елемент + темний/світлий пресет | Статичний `#RRGGBB` на елемент | Динамічні пороги (`static` / `steps` / плавний OKLab `gradient`), автоматичні токени теми та деградація (`stale` / `missing`) |
| **Поверхня віджета** | Колір-ключ (ламається в HDR) або суцільний фон | Суцільний `FillRect` + загальна прозорість | Per-pixel alpha (D2D DIB + `UpdateLayeredWindowIndirect`), закруглення кутів, обводка, padding, pill-групи, HDR-safe режим |

## 2. Архітектура конвеєра кастомізації

```
┌──────────────────┐   ┌───────────────────────┐   ┌─────────────────────┐
│ Snapshot +       │   │ Config v2 (TOML)      │   │ System Theme / DPI  │
│ HistoryRing (60s)│   │ (layout/items/style)  │   │ (Dark/Light/Accent) │
└────────┬─────────┘   └──────────┬────────────┘   └──────────┬──────────┘
         │                        │                           │
         └────────────────────────┼───────────────────────────┘
                                  ▼
                ┌───────────────────────────────────┐
                │ DisplayModelBuilder (oxide-core)  │
                │ • Резолвінг MetricSelector        │
                │ • Форматування (label/val/unit)   │
                │ • Обчислення ColorRule (OKLab)    │
                │ • Підготовка серій для Sparkline  │
                │ • Хешування моделі (Dirty Check)  │
                └─────────────────┬─────────────────┘
                                  ▼
                ┌───────────────────────────────────┐
                │ LayoutEngine (oxide-render)       │
                │ • Rows / Vertical / Grid / Groups │
                │ • Вимірювання через DirectWrite   │
                │ • Стабільна ширина цифр (tnum)    │
                └─────────────────┬─────────────────┘
                                  ▼
                ┌───────────────────────────────────┐
                │ WidgetCanvas (Direct2D / DWrite)  │
                │ • Рендер у premultiplied BGRA8 DIB│
                └────────┬─────────────────┬────────┘
                         │                 │
        (oxide-monitor)  ▼                 ▼  (oxide-settings Live Preview)
     UpdateLayeredWindowIndirect     egui::TextureHandle (RGBA8, 1x/2x/3x)
```

Ключовий принцип: **`DisplayModelBuilder` не залежить від Win32** (живе в `oxide-core`, легко покривається unit-тестами), а **`LayoutEngine + WidgetCanvas` живуть у спільному крейті `oxide-render`**, тому і реальний віджет на таскбарі, і Live Preview у вікні налаштувань виконують **ідентичний код рендерингу**.

## 3. Універсальна адресація метрик (`MetricSelector`)

Замість фіксованого `enum ItemId` з 12 значень вводимо розширюваний `MetricSource`, який підтримує інстанси конкретного заліза та зовнішні провайдери:

```toml
# Приклади джерел даних для елементів віджета:
{ kind = "net_up", adapter = "auto" }                        # або adapter_luid = 1689399632855040
{ kind = "net_down", adapter = "Wi-Fi" }
{ kind = "net_combined", adapter = "auto" }                  # для dual-sparkline (Up + Down)
{ kind = "net_today_total", adapter = "auto" }
{ kind = "cpu_usage" }
{ kind = "cpu_freq" }
{ kind = "cpu_temp", source = "auto" }                       # auto | acpi | provider
{ kind = "memory_usage" }                                    # % або GB (налаштовується display_as)
{ kind = "gpu_usage", target = { role = "discrete" } }       # primary | integrated | discrete | luid | index
{ kind = "gpu_temp", target = { role = "discrete" } }
{ kind = "gpu_vram", target = { role = "integrated" } }
{ kind = "disk_temp", target = { index = 0 } }               # PhysicalDrive0 (NVMe)
{ kind = "disk_activity", target = { index = 1 } }           # PhysicalDrive1 (SATA)
{ kind = "disk_throughput", target = { index = 0 }, dir = "rw" }
{ kind = "external_sensor", provider = "hwinfo", sensor = "CPU (Tctl/Tdie)" }
{ kind = "separator" }                                       # вертикальна/горизонтальна лінія або пробіл
```

**Стабільність при зміні індексів пристроїв:**
- Мережевий адаптер прив'язується за парою `(adapter_luid, fallback_name)`.
- GPU прив'язується за `(luid, vendor, role: integrated|discrete, fallback_name)`.
- Диск прив'язується за `(drive_index, model_hint)`. Якщо користувач дав диску короткий аліас у `[aliases]`, наприклад `"Apacer AS2280P4U 1TB" = "NVMe"`, цей аліас автоматично підставляється як дефолтний `label` (якщо користувач не перевизначив `label` вручну у конкретному елементі).

## 4. Рушій макета (`LayoutEngine v2`)

### 4.1. Режими розкладки (`layout.mode`)

1. **`flow_rows` (Автоматичні рядки — 1, 2, 3 або 4 рядки):**
   - `rows`: `1 | 2 | 3 | 4`.
   - `fill_order`: `column_major` (сумісно з TrafficMonitor: `0, 2, 4, 6` у першому рядку; `1, 3, 5, 7` у другому) або `row_major` (`0, 1, 2, 3` зверху; `4, 5, 6, 7` знизу — інтуїтивніше для новачків).
   - `column_sizing`:
     - `fit_content` (**новий дефолт**): кожна колонка отримує мінімальну стабільну ширину під найширше очікуване значення своїх елементів (напр. `100.0 Mb/s` ширше за `99%`), усуваючи зайві порожні дірки між колонками!
     - `equal` (як у TrafficMonitor / v1): усі колонки однакової ширини.
   - `width_mode`: `auto` (віджет сам підбирає точну ширину до `max_width`) або `fixed(px)`.

2. **`grid` (Довільна сітка — Drag-and-Drop матриця):**
   - Кожен елемент або група має координати `row`, `col`, `row_span` (default 1), `col_span` (default 1).
   - Це дозволяє, наприклад, поставити **високий графік мережі** на 2 рядки (`row = 0, col = 0, row_span = 2`), а праворуч від нього — 2 рядки компактних текстових метрик CPU/RAM/GPU/Temp!
   ```
   ┌──────────────┬───────────┬───────────┬────────────┐
   │  Net Graph   │ CPU:  14% │ GPU:   0% │ dGPU: 42°C │
   │  ↑ 2.7 Mb/s  ├───────────┼───────────┼────────────┤
   │  ↓ 0.3 Mb/s  │ MEM:  64% │ CPU: 48°C │ NVMe: 41°C │
   └──────────────┴───────────┴───────────┴────────────┘
   ```

3. **`vertical_auto` (Підтримка вертикального таскбара):**
   - Коли `ABM_GETTASKBARPOS` повертає `ABE_LEFT` або `ABE_RIGHT` (Windows 10 або Windows 11 з ExplorerPatcher/Windhawk), `LayoutEngine` автоматично перемикає розкладку у 1- або 2-колонковий вертикальний стек (ширина обмежена шириною таскбара, напр. 62–96 px), скорочуючи одиниці до `short_mode` за правилом `layout.vertical_override`.

4. **Логічні групи (`groups`):**
   - Елементи можна об'єднувати в іменовані групи (напр. «Мережа», «Обчислення», «Температури»).
   - Група може мати власний візуальний контейнер (напівпрозора «пігулка» `pill_bg`, тонка рамка, внутрішній `padding`) або тонкий вертикальний розділювач (`separator`) між сусідніми групами — це створює чисту візуальну ієрархію у стилі Win11 Widgets / Fluent.

## 5. Візуальні режими кожного елемента (`ItemVisual`)

Кожен елемент `[[items]]` незалежно обирає власний спосіб рендерингу:

### 5.1. `text` — Тільки текст
- Структура слота: `[Icon?] [Label] [gap] [Value][space?][Unit]`.
- Підтримка вирівнювання значення праворуч (`value_align = "right"`), що дає ідеальну вертикальну лінію в колонках.
- Можливість показувати 2 значення в одному слоті для компактності (напр. `CPU 14% · 48°C` або `MEM 10.2/16G`).

### 5.2. `text_sparkline` — Текст + міні-графік
Два варіанти розміщення графіка всередині комірки:
- **`background` (під текстом):** напівпрозора заливка (`fill_alpha = 0.22`) + лінія зверху (`stroke_width = 1.25 px`) по всій площі комірки — нуль додаткової ширини!
- **`inline_right` / `inline_left`:** міні-графік фіксованої ширини (`28–48 px`) поруч із текстом.
- **Стилі графіка:** `area` (плавна полілінія + вертикальний градієнт прозорості донизу), `line` (тільки контур), `bars` (вертикальні стовпчики по 2 px).
- **Масштабування осі Y:**
  - `fixed(0.0..100.0)` для `%`;
  - `fixed(30.0..95.0)` для температур (щоб коливання 40→75 °C були виразними);
  - `auto_decay` для швидкості мережі та дисків (динамічний максимум із плавним спаданням та мінімальною «підлогою», напр. 1 Mb/s, щоб шум у 5 Kb/s не заповнював 100% графіка).
- **Дані:** ring buffer `RingBuffer<f32, 60>` (або 120) у `oxide-sensors` — нуль алокацій у гарячому шляху; 60 точок для 16 серій займають `< 4 KB` RAM.

### 5.3. `text_progress` — Текст + прогрес-бар
- **`bar_bottom`:** тонка лінія прогресу (2–3 px, скруглені кінці) уздовж нижньої межі комірки; трек приглушений (`alpha = 0.15`), заповнення — в актуальний колір порогу (`ColorRule`).
- **`bar_background`:** заповнення фону комірки зліва направо (сучасний аналог `show_status_bar` із TrafficMonitor, але з м'яким заокругленням і per-pixel alpha).
- **`bar_inline`:** компактний горизонтальний стовпчик (`24–36 px`) між лейблом і значенням.
- **`radial_ring`:** мініатюрне кільце (`14–22 px` діаметр, кут 270° або 360°, D2D `ID2D1GeometrySink::AddArc`) поруч із текстом або навколо короткого числа — ефектно виглядає в 1-рядковому або високому 2-рядковому пресеті.

### 5.4. `graph_only` — Тільки графік
- Чистий графік без тексту (або з мікро-підписом у кутку), опційна пунктирна рамка (`dashed_border`) та сітка (`grid_lines`).
- Підтримує **dual-series** режим: наприклад, Download (зелений/блакитний зверху або основний шар) + Upload (помаранчевий/фіолетовий поверх або дзеркально вниз від центральної лінії — *mirror sparkline*).

## 6. Типографіка та усунення «стрибків» тексту

### 6.1. Окрема типографіка для `label`, `value`, `unit`
У DirectWrite це реалізується без додаткових витрат на кадр: кешується 3 об'єкти `IDWriteTextFormat` (або per-item overrides при зміні конфіга) і застосовуються діапазони `IDWriteTextLayout::SetFontWeight` / `SetFontSize` / `SetDrawingEffect`:

- **`label` (підпис, напр. `CPU:`):** менший розмір (напр. `7.5 pt`), нормальна або легка насиченість (`weight = 400`), приглушений колір (`#9AA6B2`).
- **`value` (число, напр. `48.2`):** основний розмір (`8.5–9.0 pt`), напівжирний (`weight = 600`), високий контраст або колір порогу.
- **`unit` (одиниця виміру, напр. `Mb/s`, `°C`, `%`, `GHz`):** компактніший розмір (`7.0–7.5 pt`), `weight = 400`, знижена прозорість (`alpha = 0.72`).

Така 3-рівнева типографічна ієрархія миттєво підвищує читабельність щільного віджета (око одразу чіпляє числа, а підписи й одиниці не створюють візуального шуму).

### 6.2. Моноширинні цифри (`tabular-nums`) у DirectWrite
Головна візуальна проблема системних моніторів у пропорційному шрифті (`Segoe UI` / `Segoe UI Variable`) — цифра `1` вужча за `8`, через що `11.1 Mb/s` і `88.8 Mb/s` постійно «смикають» рядок вліво-вправо.

**Рішення в DirectWrite (`windows` 0.62):**
1. Створити один спільний `IDWriteTypography` на весь рендерер із фічею `DWRITE_FONT_FEATURE_TAG_TABULAR_FIGURES` (`'tnum'`, `parameter = 1`).
2. Застосувати `text_layout.SetTypography(&tabular_typography, range)` до числової частини (`value`). `Segoe UI`, `Segoe UI Variable`, `Inter`, `Cascadia Code`, `JetBrains Mono` нативно підтримують OpenType-таблицю `tnum`!
3. Для шрифтів, які не мають `tnum`, `LayoutEngine` обчислює `max_digit_advance` (ширину цифри `'0'`) і за потреби вирівнює числове поле по правій межі фіксованого слота (`min_chars = config.format.digits`), тому позиція лейбла й одиниці виміру **ніколи не зсувається**.

## 7. Динамічні пороги кольору (Conditional Coloring)

Замість одного статичного `color = "#F0A050"` кожен елемент підтримує гнучке правило `color_rule`:

### 7.1. Режими `ColorRule`
1. **`static`:** фіксований `#RRGGBB`, `#RRGGBBAA` або семантичний токен теми (`"theme.value"`, `"theme.accent"`, `"theme.label"`).
2. **`steps` (дискретні зони):**
   ```toml
   [items.color_rule]
   mode = "steps"
   stops = [
     { at = 0.0,  color = "#7FD37F" }, # зелений (< 60 °C)
     { at = 60.0, color = "#F0C674" }, # жовтий (60–80 °C)
     { at = 80.0, color = "#F26D6D" }, # червоний (≥ 80 °C)
   ]
   ```
3. **`gradient` (плавний перехід між точками):**
   - Інтерполяція виконується у перцептивно рівномірному колірному просторі **OKLab** (чиста функція ~25 рядків на `f32`, без залежностей).
   - Чому OKLab, а не sRGB? При лінійному змішуванні зеленого `#4ADE80` → червоного `#EF4444` у sRGB посередині виходить тьмяний коричнево-сірий колір; в OKLab перехід природно йде через яскравий читабельний жовто-бурштиновий із збереженням контрастності!
4. **Пріоритет станів якості даних:**
   - `Quality::Missing` (`None`) → `—` у кольорі `theme.muted` (ігнорує `color_rule`).
   - `Quality::Stale` (> 5 с без оновлення) → значення з суфіксом `~` і 50% прозорістю.
   - `Quality::Suspect` (наприклад, ACPI-зона, що «залипла») → іконка/суфікс попередження і приглушений тон.

## 8. Стилізація поверхні віджета (`[surface]`)

Оскільки рендер переходить на Direct2D у premultiplied BGRA8 DIB + `UpdateLayeredWindowIndirect`:

- **Фон (`background_mode`):**
  - `transparent` — повністю прозорий фон (текст і елементи малюються прямо поверх таскбара Win11; ідеально вписується у системний Acrylic/Mica таскбар!). Для читабельності додається опційна м'яка мікротінь тексту (`text_shadow = true`, 1 px зміщення, `alpha = 0.35`).
  - `solid_auto` — автоматичний колір із `SystemUsesLightTheme` (`#202020` / `#F3F3F3`) з налаштовуваною прозорістю `opacity` (`0..255`).
  - `custom` — довільний `#RRGGBBAA` користувача.
  - `hdr_safe` — примусово непрозорий фон (вирішує проблему зникнення/пересвіту layered-вікон при увімкненому Windows HDR, зафіксовану в `05_current_setup_audit.md` §9.5).
- **Геометрія поверхні:** `corner_radius` (`0..16 px`), `border_width` (`0..2 px`), `border_color` (`#RRGGBBAA` або `theme.border`), `padding = { top, right, bottom, left }`, `cell_padding`, `gap_x`, `gap_y`.
- **Кастомне зображення (для імпортованих скінів):** опційний `background_image` (PNG через WIC / `image`), масштабований за 9-slice або fit.

## 9. Live Preview у реальному часі (Pixel-Perfect)

Ключова інженерна вимога — користувач у вікні налаштувань має бачити **абсолютно точну копію віджета** миттєво при кожному русі слайдера, зміні шрифту чи перетягуванні елемента, без перезапуску програми.

### 9.1. Спільний крейт `oxide-render`
Виділяємо рендеринг із `oxide-ui` у самостійний крейт **`oxide-render`** (залежить лише від `oxide-core` та `windows` D2D/DWrite/GDI):

```rust
// Інтерфейс спільного рендерера (концепт)
pub struct WidgetRenderer { /* ID2D1Factory1, IDWriteFactory, IDWriteTypography, DIB */ }

pub struct RenderedFrame {
    pub width: u32,
    pub height: u32,
    pub bgra_premultiplied: &[u8], // готово для UpdateLayeredWindowIndirect
}

impl WidgetRenderer {
    pub fn render_to_buffer(
        &mut self,
        config: &Config,
        snapshot: &Snapshot,
        history: &HistoryView,
        theme_ctx: &SystemThemeContext,
        dpi: u32,
    ) -> Result<RenderedFrame<'_>, RenderError>;
}
```

### 9.2. Як це працює в `oxide-settings.exe`
1. `oxide-settings.exe` має власний екземпляр `WidgetRenderer` (працює на CPU через `ID2D1DCRenderTarget`, **не** створює конфліктів із `wgpu` вікна `egui` і займає `< 1 ms` на кадр розміром 350×40 px!).
2. Коли користувач змінює будь-яке поле в `draft_config` або приходить новий 1 Hz `Snapshot` по Named Pipe:
   - `oxide-settings.exe` викликає `renderer.render_to_buffer(&draft_config, &preview_snapshot, ...)` за **< 0.5 ms**;
   - перетворює BGRA premultiplied → `egui::ColorImage` (простий swizzle `B↔R` на ~14K пікселів ≈ 0.02 ms);
   - оновлює `egui::TextureHandle` і відображає її в закріпленій верхній панелі **Live Preview**.
3. **Інтерактивні «фішки» панелі Live Preview:**
   - **Імітація підкладки таскбара:** перемикач фону під віджетом — *Темний таскбар Win11*, *Світлий таскбар Win11*, *Кольорові шпалери (градієнт)*, *Шахова прозорість* — щоб одразу бачити, як працює прозорість і тінь тексту.
   - **Масштаб інспекції:** `100%` (1:1 як на екрані), `150%`, `200%` (піксельний зум для точного налаштування відступів і шрифтів).
   - **Симулятор навантаження (Threshold Tester):** перемикач `Живі дані` ↔ `Тестовий стенд` зі слайдером «Стрес 0% → 100%» (штучно змінює CPU/RAM/Temp/Net у `preview_snapshot`), щоб користувач міг одразу перевірити свої градієнти порогів кольору (`60°C → 85°C`) без потреби запускати бенчмарк на ПК!
   - **Жива синхронізація з реальним таскбаром (опція «Застосовувати на льоту»):** при зміні `draft_config` з debounce **50 ms** відправляється IPC-повідомлення `PreviewConfig(draft_config)` у `oxide-monitor.exe`. Фоновий віджет миттєво перемальовується в пам'яті **без запису на диск**. Натискання **«Зберегти»** фіксує `config.toml` атомарно; натискання **«Скасувати»** (або закриття без збереження) шле `RevertConfig`, і таскбар миттєво повертається до збереженого стану.

### 9.3. Вплив на продуктивність фонового віджета (`oxide-monitor.exe`)
- Перехід на `oxide-render` (Direct2D DC render target + кешування `IDWriteTextFormat`, `ID2D1SolidColorBrush`, `IDWriteTypography` + dirty-хеш `DisplayModel`) гарантує `< 0.25% CPU` у текстовому режимі і `< 0.6% CPU` з активними sparklines при 1 Hz.
- Якщо конфіг не використовує графіки, кільцеві буфери історії залишаються крихітними (~4 KB) і не витрачають часу на рендер геометрії.
